# Sqoch — оформление билетов

Тестовое задание «Тест 01 / Код и интерфейс»: покупка билетов на мероприятие на моковых данных.

## Запуск

Нужен Node.js 20.19+ или 22.12+.

```bash
npm install
npm run dev          # http://localhost:5173
```

Полезные адреса:

- `http://localhost:5173/` — обычный сценарий, на «сервере» 50 мест;
- `http://localhost:5173/?seats=1` — стартовать с одним свободным местом;
- `http://localhost:5173/?seats=0` — мероприятие уже распродано.

## Как показать сценарии

**Успешное оформление.** Заполнить участников и email → «Перейти к проверке» → «Подтвердить и оплатить».

**Места закончились перед подтверждением.** Дойти до шага «Проверка», внизу страницы открыть
жёлтый пульт «Демо: другие покупатели» и нажать «Оставить 1 место» (или «Раскупить всё»).
Пульт меняет остаток только на мок-сервере — покупатель, как в жизни, узнаёт об этом при подтверждении.
Если место ещё есть, можно уменьшить заказ и оформить его заново; данные не теряются.
Если мест не осталось совсем, можно «Проверить места снова» (в пульте — «Вернуть 50 мест»).

## Видео

В `demo/` — записи сценариев на компьютере (1280 px) и телефоне (360 px):

| Файл | Что показывает |
| --- | --- |
| `*-успешное оформление.webm` | ошибки валидации, правило «ребёнок + взрослый», проверка, правка, подтверждение |
| `*-места закончились перед подтверждением.webm` | отказ сервера, уменьшение заказа, повторное подтверждение |
| `*-распроданное мероприятие.webm` | мест нет уже при открытии |

Перезаписать: `npm run demo:record`.

## Проверки

```bash
npm run check        # типы + линтер + unit/интеграционные тесты (Vitest)
npm run test:e2e     # сквозные тесты в Chromium на 1280 и 360 px (Playwright)
```

Перед первым `test:e2e` может понадобиться `npx playwright install chromium`.

## Устройство

```
src/
  domain/order.ts        правила заказа: цены, возраст, «ребёнок + взрослый», лимиты, валидация
  api/ticketApi.ts       мок бэкенда: остаток мест в памяти, задержка сети, отказ «sold_out»
  App.tsx                шаги: участники → проверка → результат (успех / места закончились)
  components/            экраны и части интерфейса
  ui/format.ts           рубли, склонения («3 года», «осталось 1 место»), дата
e2e/checkout.spec.ts     сквозные сценарии и запись видео
```

- Вся бизнес-логика — чистые функции в `domain/order.ts`, интерфейс только показывает результат `validateOrder`.
- Клиент проверяет заказ заранее, но окончательно места подтверждает «сервер» (`placeOrder`):
  остаток мог измениться, пока человек заполнял форму.
- Черновик заказа живёт в `App` и переживает переходы между шагами — поэтому «Изменить данные»
  возвращает к форме со всеми введёнными данными.

## Правила и как я их понял

| Правило | Реализация |
| --- | --- |
| 1–4 участника | кнопка «Добавить участника» блокируется на 4 (или на остатке мест, если он меньше) |
| 2 000 ₽ с 14 лет, 1 000 ₽ младше 14 | цена видна сразу под полем возраста |
| Ребёнок только с участником от 18 лет | «ребёнок» — младше 14 (детский билет); подросткам 14–17 сопровождающий не нужен — в задании этого нет |
| Имя и возраст у каждого, один email | возраст — целое 0–120, email проверяется по формату |
| Состав заказа и итог, правка до подтверждения | шаг «Проверка» + кнопка «Изменить данные» |
| Успех и «закончились места» | экран с номером заказа; экран отказа с остатком мест и выходом из ситуации |
| Компьютер и 360 px | вёрстка от телефона, e2e проверяет отсутствие горизонтальной прокрутки |

Цены, возрастные границы и лимит участников — константы в начале `domain/order.ts`; тексты интерфейса берут их оттуда.

Доступность: подписи у всех полей, ошибки связаны с полями через `aria-describedby`, фокус уходит
на первое ошибочное поле, при смене шага — на заголовок нового шага, после удаления участника — на «Добавить участника».

## Время и незавершённое

Фактически: около 20 минут — код, тесты, вёрстка и видео сделаны вместе с ИИ-ассистентом (Claude Code), я ставил задачу, проверял и принимал решения.

Сознательно не делал (вне мока):

- настоящий бэкенд — мок в памяти, после перезагрузки страницы места восстанавливаются;
- настоящую оплату и отправку писем — подтверждение заказа сразу считается оплатой;
- бронь мест на время оформления — в жизни её стоит делать на сервере, чтобы реже показывать отказ;
- сохранение черновика при перезагрузке страницы.
